## 배포가 너무 번거로웠다

프로젝트를 운영하다 보면 배포 작업이 생각보다 손이 많이 간다.

매번 Docker 이미지를 빌드하고, 버전 태그를 달고, Docker Hub에 푸시하고, GitHub Release를 만들고 더군다나 전문적으로 배운게 아닌 온라인과 주변사람들에게 물어물어 얻은 지식이다 보니 규격화도 필요했다.

이 과정을 손으로 하나하나 진행하다 보면 실수도 생기고 시간도 오래 걸린다.

그래서 이번에 GitHub Actions를 활용해서 배포 과정을 자동화하는 워크플로우를 구성해봤다.

---

## GitHub Actions이 뭘까?

GitHub Actions는 GitHub에서 제공하는 CI/CD(지속적 통합/배포) 도구다.

쉽게 말하면 "GitHub 저장소에서 특정 이벤트가 발생하면 자동으로 작업을 실행해주는 시스템"이라고 볼 수 있다.

예를 들어:
- 코드를 push하면 → 자동으로 테스트 실행
- 태그를 만들면 → 자동으로 배포 진행
- Pull Request를 열면 → 자동으로 코드 검사

개발자가 아니더라도 "GitHub에서 이런 일이 생기면 → 저런 작업을 자동으로 해줘"라고 이해하면 된다.

## 워크플로우 구성 전 준비 사항

본격적으로 워크플로우를 만들기 전에 몇 가지 준비할 것들이 있다.

### 1. Docker Hub 계정 준비

Docker 이미지를 저장할 공간이 필요하다.

[Docker Hub](https://hub.docker.com)에서 계정을 만들고, Access Token을 발급받아야 한다.

**Access Token 발급 방법:**
1. Docker Hub 로그인
2. Account Settings → Security → New Access Token
3. 토큰 이름 입력하고 생성
4. 생성된 토큰을 **반드시 복사해서 저장** (다시 볼 수 없음!)
※ 토큰은 절대절대 유출하면 안되고 AI한테 보여줘서도 안된다.

### 2. GitHub Secrets 설정

민감한 정보(Docker Hub 계정 정보)를 코드에 직접 넣으면 안 되니, GitHub Secrets에 저장한다.

GitHub 저장소에서 `Settings → Secrets and variables → Actions`로 이동해서 다음 두 개를 등록한다:

| Secret 이름 | 값 |
|------------|-----|
| `DOCKERHUB_USERNAME` | Docker Hub 사용자명 |
| `DOCKERHUB_TOKEN` | 방금 발급받은 Access Token |

![Secrets 설정 화면 예시](https://docs.github.com/assets/cb-45016/images/help/repository/actions-secrets-add.png)

### 3. CHANGELOG.md 파일 준비

버전별 변경 사항을 기록하는 파일이다.

프로젝트 루트에 다음과 같은 형식으로 작성한다:

```markdown
# Changelog

## [v26.03.01] - 2026-03-26

### Added
- 사용자 로그인 기능 추가
- 프로필 이미지 업로드 기능

### Fixed
- 회원가입 시 이메일 중복 체크 오류 수정

---

## [v26.02.15] - 2026-02-15

### Changed
- 메인 화면 레이아웃 개선
```

※ `## [v버전]` 형식을 반드시 지켜야 자동 추출이 가능하다.

원래는 v1.0.0 같은 형식을 썼지만 v.연도.월.n번째 릴리즈 형식이 사용 시 관리가 편해서 변경하였다.

### 4. 배포 관련 파일 준비

루트 디렉토리에 다음 파일들이 있어야 한다:
- `docker-compose.yml` — 배포용 설정 파일
- `.env.example` — 환경 변수 샘플 파일

이 파일들은 나중에 릴리즈 첨부 파일로 자동 업로드된다.

## 워크플로우 파일 만들기

이제 본격적으로 워크플로우를 만들어보자.

프로젝트에 `.github/workflows/` 디렉토리를 만들고, 그 안에 `docker-build.yml` 파일을 생성한다.

```
your-project/
├── .github/
│   └── workflows/
│       └── docker-build.yml   ← 여기에 작성
├── CHANGELOG.md
├── docker-compose.yml
└── .env.example
```

## 워크플로우 기본 구조 이해하기

워크플로우 파일은 YAML 형식으로 작성한다.

크게 다음과 같은 구조를 가진다:

```yaml
name: 워크플로우 이름

on: 언제 실행할지 (트리거)

env: 환경 변수 설정

jobs: 실제로 수행할 작업들
```

하나씩 살펴보자.

### 트리거 설정

워크플로우를 언제 실행할지 정의한다.

```yaml
on:
  push:
    branches: [ main ]      # main 브랜치에 push할 때
    tags: [ 'v*' ]          # v로 시작하는 태그를 push할 때 (예: v1.0.0)
  workflow_dispatch:        # 수동 실행 허용
```

이렇게 설정하면:
- main 브랜치에 코드를 push할 때마다 → Docker 이미지 빌드
- `v1.0.0` 같은 태그를 push하면 → Docker 이미지 빌드 + GitHub Release 생성
- 필요하면 수동으로도 실행 가능

### 환경 변수 설정

자주 사용하는 값들을 미리 정의해둔다.

```yaml
env:
  BACKEND_IMAGE_NAME: your-dockerhub-username/project-backend
  FRONTEND_IMAGE_NAME: your-dockerhub-username/project-frontend
  GITHUB_REPO: your-github-username/your-repo-name
```

※ 여기서 `your-dockerhub-username`, `your-github-username` 등은 실제 값으로 바꿔야 한다.

## Job 1: Backend 이미지 빌드

첫 번째 작업은 Backend Docker 이미지를 빌드하고 Docker Hub에 업로드하는 것이다.

```yaml
jobs:
  build-and-push-backend:
    runs-on: ubuntu-latest    # Ubuntu 환경에서 실행

    steps:
      - name: 코드 가져오기
        uses: actions/checkout@v4
```

### Docker Buildx 설정

멀티 플랫폼 빌드를 지원하는 도구를 설정한다.

```yaml
      - name: Docker Buildx 설정
        uses: docker/setup-buildx-action@v3
```

### Docker Hub 로그인

앞서 설정한 Secrets를 이용해서 Docker Hub에 로그인한다.

```yaml
      - name: Docker Hub 로그인
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}
```

`${{ secrets.XXX }}` 형식으로 Secret 값을 안전하게 사용할 수 있다.

### 메타데이터 추출

Docker 이미지에 붙일 태그를 자동으로 생성한다.

```yaml
      - name: 메타데이터 추출
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.BACKEND_IMAGE_NAME }}
          tags: |
            # main 브랜치 push 시 latest 태그
            type=raw,value=latest,enable={{is_default_branch}}
            # 태그 push 시 버전 태그
            type=match,pattern=v(\d+\.\d+\.\d+),group=1
```

이렇게 하면:
- main 브랜치 push → `your-image:latest`
- v1.2.3 태그 push → `your-image:1.2.3`

### 이미지 빌드 및 푸시

실제로 Docker 이미지를 빌드하고 Docker Hub에 업로드한다.

```yaml
      - name: Backend 이미지 빌드 및 푸시
        uses: docker/build-push-action@v5
        with:
          context: ./backend           # Dockerfile 위치
          file: ./backend/Dockerfile   # Dockerfile 경로
          push: true                   # Docker Hub에 푸시
          tags: ${{ steps.meta.outputs.tags }}
          platforms: linux/amd64       # 빌드할 플랫폼
          cache-from: type=registry,ref=${{ env.BACKEND_IMAGE_NAME }}:buildcache
          cache-to: type=registry,ref=${{ env.BACKEND_IMAGE_NAME }}:buildcache,mode=max
```

`cache-from`과 `cache-to`는 빌드 속도를 높이기 위한 캐싱 설정이다.

※ 프로젝트에 Backend만 있다면 Frontend 관련 부분은 삭제하면 된다.

## Job 2: Frontend 이미지 빌드

Frontend도 Backend와 동일한 방식으로 빌드한다.

```yaml
  build-and-push-frontend:
    runs-on: ubuntu-latest
    steps:
      # Backend와 동일한 단계
      # context와 file 경로만 ./frontend로 변경
```

※ 단일 서비스 프로젝트라면 이 Job은 생략하면 된다.

## Job 3: GitHub Release 자동 생성

마지막으로 태그를 push했을 때 자동으로 GitHub Release를 만드는 작업이다.

```yaml
  create-release:
    needs: [build-and-push-backend, build-and-push-frontend]
    runs-on: ubuntu-latest
    if: startsWith(github.ref, 'refs/tags/v')
```

`needs`는 이전 작업들이 성공해야 실행된다는 의미다.

`if` 조건으로 태그 push일 때만 실행되도록 제한한다.

### 버전 정보 추출

태그에서 버전 번호를 추출한다.

```yaml
    steps:
      - name: 코드 가져오기
        uses: actions/checkout@v4

      - name: 버전 추출
        id: version
        run: echo "VERSION=${GITHUB_REF#refs/tags/v}" >> $GITHUB_OUTPUT
```

`refs/tags/v1.2.3`에서 `1.2.3`만 추출한다.

### CHANGELOG 자동 추출

CHANGELOG.md에서 해당 버전의 변경 사항만 추출한다.

```yaml
      - name: 릴리즈 노트 추출
        id: changelog
        run: |
          VERSION="${GITHUB_REF#refs/tags/v}"
          NOTES=$(awk "/^## \[v${VERSION}\]/{found=1; next} /^## \[/{if(found) exit} found{print}" CHANGELOG.md)
          {
            echo "NOTES<<EOF"
            echo "$NOTES"
            echo "EOF"
          } >> $GITHUB_OUTPUT
```

이 스크립트는 CHANGELOG.md에서 `## [v1.2.3]` 섹션을 자동으로 찾아서 내용을 가져온다.

### Release 생성

추출한 정보를 바탕으로 GitHub Release를 생성한다.

```yaml
      - name: GitHub Release 생성
        uses: softprops/action-gh-release@v1
        with:
          files: |
            docker-compose.yml
            .env.example
          body: |
            ## 변경 사항

            ${{ steps.changelog.outputs.NOTES }}

            ---

            ## 빠른 시작 (신규 설치)

            ```bash
            mkdir my-project && cd my-project
            curl -LO https://github.com/${{ env.GITHUB_REPO }}/releases/download/v${{ steps.version.outputs.VERSION }}/docker-compose.yml
            curl -LO https://github.com/${{ env.GITHUB_REPO }}/releases/download/v${{ steps.version.outputs.VERSION }}/.env.example

            cp .env.example .env
            # .env 파일 수정 후 실행
            docker compose up -d
            ```

            ## Docker Images

            ```
            docker pull ${{ env.BACKEND_IMAGE_NAME }}:${{ steps.version.outputs.VERSION }}
            docker pull ${{ env.FRONTEND_IMAGE_NAME }}:${{ steps.version.outputs.VERSION }}
            ```
```

이렇게 하면 Release 페이지에 배포 가이드까지 자동으로 작성된다.

## 실제 사용 방법

이제 모든 설정이 끝났다.

실제로 배포할 때는 다음 순서로 진행한다.

### 1. CHANGELOG.md 업데이트

```markdown
## [v1.2.0] - 2026-03-26

### Added
- 사용자 알림 기능 추가

### Fixed
- 로그아웃 후 세션 만료 오류 수정
```

### 2. 버전 태그 생성 및 Push

```bash
# 변경 사항 커밋
git add CHANGELOG.md
git commit -m "chore: release v1.2.0"

# 태그 생성
git tag v1.2.0

# Push (main 브랜치와 태그 모두)
git push origin main
git push origin v1.2.0
```

### 3. 자동 실행 확인

GitHub 저장소의 `Actions` 탭에서 워크플로우 실행 상태를 확인할 수 있다.

![GitHub Actions 실행 화면](https://docs.github.com/assets/cb-24090/images/help/actions/workflow-run-selected-run.png)

성공하면:
1. Docker Hub에 새 이미지가 업로드됨
2. GitHub Releases에 새 릴리즈가 생성됨
3. 릴리즈에 `docker-compose.yml`과 `.env.example` 파일이 첨부됨

## CalVer 버전 관리 방식

일반적인 SemVer(1.2.3) 대신 CalVer(26.03.01) 형식을 사용할 수도 있다.

CalVer는 날짜 기반 버전 관리 방식으로, 다음과 같은 형식을 사용한다:

```
v26.03.01
│  │  └── 일련번호
│  └───── 월
└──────── 년도 (2026 → 26)
```

### CalVer 사용 시 주의 사항

**문제:** `type=semver` 액션은 `v26.03.01`을 `26.3.1`로 변환해버린다 (leading zero 제거).

**해결:** `type=match`를 사용해서 원본 형식을 보존한다.

```yaml
tags: |
  # ❌ 잘못된 방법 - v26.03.01 → 26.3.1
  type=semver,pattern={{version}}

  # ✅ 올바른 방법 - v26.03.01 → 26.03.01
  type=match,pattern=v(\d+\.\d+\.\d+),group=1
```

## 단일 서비스 프로젝트 적용

Backend만 있는 프로젝트라면 다음과 같이 수정한다:

1. `build-and-push-frontend` job 전체 삭제
2. `create-release` job의 `needs` 수정:

```yaml
  create-release:
    needs: [build-and-push-backend]  # frontend 제거
```

3. Release body에서 Frontend 이미지 pull 명령어 제거

## 자주 발생하는 문제 해결

### Docker Hub 로그인 실패

**증상:** `unauthorized: authentication required` 에러

**해결:**
1. Docker Hub Token이 올바르게 설정되었는지 확인
2. Token 권한에 "Read, Write, Delete" 포함 여부 확인
3. GitHub Secrets에 오타가 없는지 확인

### CHANGELOG 추출 실패

**증상:** Release 본문이 비어있음

**해결:**
1. CHANGELOG.md에 `## [v버전]` 형식이 정확한지 확인
2. 버전 번호 일치 여부 확인 (태그가 v1.2.0이면 CHANGELOG도 [v1.2.0])

### 권한 오류

**증상:** `Resource not accessible by integration` 에러

**해결:**
워크플로우 파일 상단에 권한 설정 추가:

```yaml
permissions:
  contents: write
  packages: write
```

## 추가 팁

### 수동 실행 옵션 추가

긴급 배포가 필요할 때를 위해 수동 실행 옵션을 추가할 수 있다.

```yaml
on:
  workflow_dispatch:
    inputs:
      version:
        description: '배포할 버전 (예: v1.2.3)'
        required: true
```

이렇게 하면 GitHub Actions 탭에서 "Run workflow" 버튼으로 수동 실행이 가능하다.

### 알림 추가

Slack이나 Discord로 배포 완료 알림을 받을 수 있다.

```yaml
      - name: Slack 알림
        if: always()
        uses: 8398a7/action-slack@v3
        with:
          status: ${{ job.status }}
          text: 'Release ${{ steps.version.outputs.VERSION }} ${{ job.status }}'
          webhook_url: ${{ secrets.SLACK_WEBHOOK_URL }}
```

※ `SLACK_WEBHOOK_URL` Secret을 미리 등록해야 한다.

## 마무리

GitHub Actions를 활용한 자동 배포 환경을 구축해봤다.

처음 설정할 때는 복잡해 보일 수 있지만, 한 번 구성해두면 매번 배포할 때마다 엄청난 시간을 절약할 수 있다.

이제 태그만 push하면:
1. Docker 이미지 자동 빌드
2. Docker Hub 자동 업로드
3. GitHub Release 자동 생성
4. 배포 가이드 자동 작성

모든 과정이 자동으로 진행된다.

더 이상 수동으로 배포 과정을 반복할 필요가 없어졌고, 실수로 인한 오류도 크게 줄어들었다.

물론 아직 이걸 수동으로 작성하기엔 실수도 많아서 여태까지는 위 내용을 기반으로 CLAUDE CODE의 도움을 받아 Workflow를 작성했다.

앞으로 더 많은 프로젝트에 이 워크플로우를 적용할 계획이다.
